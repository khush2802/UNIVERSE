# My Software Universe

Interactive developer portfolio that generates project entries from GitHub
repositories.

This is **chunk 01 — foundation and design system**. It runs, but most
sections are deliberately empty placeholders naming the chunk that fills them.

## Run it

You need Node 18.18 or newer. Check with `node -v`; if it's missing or
older, install the LTS from https://nodejs.org.

```bash
cd khush-universe
npm install
npm run dev
```

Open http://localhost:3000.

If anything fails, copy the whole error and send it back — that's expected
on a first run and quick to fix.

## Where the palette lives

`src/app/globals.css`, in the `@theme` block. Every colour in the project
resolves back to a variable there — change it once and it changes
everywhere. Domain accents are also mapped in `src/lib/domains.ts`, which
is the single definition of the six universe domains.

Three surface tiers exist on purpose, and they are not interchangeable:

- `.glass` — floating chrome only (nav, panels above the 3D scene)
- `.panel` — structured content in the page flow
- `.plate` — data, diagrams, technical readouts

Using one card style for everything is what makes a portfolio look
templated. Pick the tier that matches what the content *is*.

# Chunk 02 — data contract

Types, runtime schemas and the data seam. No UI changes.

## The seam

Nothing imports fixtures or the database directly. Everything calls
`getDataSource()` in `src/lib/dataSource.ts`. Chunk 12 swaps the in-memory
implementation for Prisma and no component changes.

## Fixtures are not your projects

`src/data/fixtures.ts` holds six records that exist to exercise every
state the analyser can produce — all six `DataLayer` kinds, a hidden
project, a low-confidence classification, and one repository so sparse
that nothing could be determined from it.

They are **not** scraped versions of your repositories, and they must
never be published. Every record carries `isFixture: true`, and
`dataSource` strips them from any production build unless
`NEXT_PUBLIC_ALLOW_FIXTURES=true` is set explicitly.

Your real project records arrive at chunk 17, generated by the analyser.

## Why the data layer is a union

`DataLayer` is a discriminated union rather than an object with optional
fields. Spec §28 says the six states are genuinely different; §33 and §34
forbid inventing a schema. With a union, rendering SQL tables for a vector
store is a compile error, so the honesty rule is enforced by the type
system instead of by review.

## Why the schemas are hand-written

`src/lib/schemas.ts` mirrors the types by hand rather than being derived
from them. A schema generated from the types would accept exactly what the
types accept, which defeats the purpose — the schema is where the extra
constraints live: confidence within 0–1, a confirmed claim must cite a
file, every architecture edge must connect two declared nodes.

That last one matters. A model that invents an edge to a node it never
declared has hallucinated part of the architecture, and the whole run is
rejected rather than partially trusted.

Nothing here repairs bad output. A `sql` layer with no tables fails
validation; it is not quietly downgraded to `unknown`. Per §42, a failed
analysis produces no project rather than a half-invented one.

## Deterministic placement

`src/lib/hash.ts` derives orbital position from the project id (§49), so a
project sits in the same place forever without storing coordinates.
Siblings are spread evenly around the ring first and then jittered by the
hash — pure hashing alone clumps, and with six projects you reliably get
two nearly on top of each other.

## The entrance is CSS, not GSAP

The spec says use GSAP here (§12). I didn't, for one reason: the hero is
the largest contentful paint on the page. Loading a JavaScript animation
library before first paint delays precisely the thing it exists to
animate. A seven-step staggered fade is six lines of CSS, runs on the
compositor, and needs no JavaScript at all.

GSAP still gets installed — at chunk 09, where the cinematic project
transitions and ScrollTrigger genuinely need it. That's below the fold and
after first paint, so it costs nothing on load.

If you'd rather follow the spec exactly, say so and I'll swap it; the
markup won't change, only the mechanism.

## The starfield is canvas, not Three.js and not DOM nodes

Three hundred absolutely-positioned divs each with their own animation is
three hundred things for the compositor to track, and it shows on a
mid-range phone. One canvas is one layer.

It's also deliberately not Three.js. WebGL arrives at chunk 04, below the
fold, where a 3D scene actually needs it. Pulling in a WebGL runtime to
draw dots above the fold is weight for nothing.

Behaviour: star count scales with viewport area so a phone doesn't draw a
desktop's worth, DPR is capped at 2, the loop stops when the tab is
hidden, and reduced motion renders one static frame — the field is still
there, it just doesn't move (§52).

## Missing profile data is loud in development, invisible in production

The hero omits fields that are `null` rather than inventing them (§62).
The failure mode that creates is that an incomplete hero looks
*intentional* — which is exactly how a placeholder ships unnoticed.

So there's a dashed panel in development listing every empty field. It
returns `null` in production. Fill in `data/profile.ts` and both the panel
and the gaps disappear on their own; no component needs editing.

Currently missing: `role`, `intro`, and all four social links.

## The palette is not duplicated in the 3D code

`readCssColor()` reads the domain accents out of the CSS custom properties
at mount and hands them to Three.js. Hardcoding hex values in the scene
would mean the palette lives in two places, and the universe would quietly
stop matching the site the first time a colour changed. §8 asks for one
central palette; this keeps that true inside WebGL too.

## Performance (§50)

- Stars are a single `Points` object — one draw call, not one mesh per star
- DPR capped at 2
- Star count halves below 768px
- Scene is lazy-loaded and only mounts within 600px of the viewport
- The frame loop stops entirely when the section is off screen
- Orbit rings are line loops, not tori
- No post-processing; the planet rim glow is a backside sphere

## Reduced motion (§52)

Nothing orbits, nothing rotates, nothing pulses. The frame loop switches to
`demand`, so it renders once and then stops. The universe is still there and
still legible — it is a still photograph of a system rather than an animation
of one.

## The domain list is real text, always

Under the canvas there is an ordinary `<ul>` of the six domains. It is not a
fallback that appears on failure — it is always rendered. §61 forbids putting
critical information only inside the 3D scene, and a screen reader gets
nothing at all from a canvas.

## Changed

| File | Why |
|---|---|
| `src/lib/domains.ts` | `projects` domain renamed to `other`; category mapping added. |
| `src/components/universe/Scene.tsx` | Camera rig, hover, selection, dimming, screen projection. |
| `src/components/universe/UniverseCanvas.tsx` | Owns interaction state; renders labels and fallback. |
| `src/data/fixtures.ts` | Two records remapped off the removed domain. |

## The domain restructure

§13 lists "Projects" as one of the six domains. §16 says every project
becomes a planet orbiting its category. Both cannot hold: if every project
orbits a single Projects planet, the AI, Web and DSA planets have nothing
orbiting them and are decoration.

So projects orbit their category, and the sixth domain is **Other** — a
catch-all rather than a bucket. `CATEGORY_TO_DOMAIN` does the mapping:
`ai→AI`, `web`/`backend`→`Web`, `dsa→DSA`, `cloud`/`devtool`/`other`→`Other`.

This is what makes the layout carry information. Which planet has the most
moons tells a visitor where the work actually is; one combined bucket would
tell them nothing.

## One state, three views

`UniverseCanvas` owns hover and selection. The 3D scene, the flat SVG map
and the HTML buttons all read the same state, so selection behaves
identically however you reached it — and a device without WebGL loses the
visuals, not the functionality.

The HTML buttons are always rendered, not shown on failure. They are the
keyboard and screen-reader path into the universe, and §61 forbids putting
critical information only inside the 3D scene.

## Camera

Lerped toward its target each frame, which gives ease-out for free: the
remaining gap shrinks every frame, so the approach decelerates on its own.
Scaled by `delta` so it moves at the same speed on a 60Hz and a 144Hz
display.

It only ever moves between two states, home and one focused planet, because
§15 warns against excessive camera movement. The focus position sits off to
one side and slightly above rather than head-on — straight in front, a
planet is a flat disc and its orbit is invisible.

Selecting a planet freezes the orbits. A planet that kept moving while
being inspected would force the camera to chase it, which reads as drift
rather than focus.

## Labels are HTML, not 3D text

Real text stays crisp at any zoom and can be read by a screen reader;
neither is true of text drawn into a canvas. Positions are written straight
to DOM refs each frame rather than through React state — sixty state
updates a second, each re-rendering six labels, would cost more than the
CSS transform it produces.

## Mobile (§53)

Under 768px the WebGL scene doesn't mount at all. The flat map plus the
buttons are the universe, and the panel becomes a bottom sheet. This isn't
degradation — a phone gets a layout suited to a thumb rather than a
shrunken desktop scene, and it skips downloading Three.js entirely.

## What the panel doesn't say

It doesn't show a project count. Zero projects have been analysed, and
"0 projects" is a claim about reality rather than a description of the
current state (§62). Chunk 06 fills it from the data source.

## Adding a project adds a planet

A project becomes a moon orbiting its category's domain planet, with its
own ring. Nothing is placed by hand (§4, §48):

```
category → CATEGORY_TO_DOMAIN → parent planet
project id → hash → angle, radius, size, spin
```

Because the moon is a *child* of the domain planet's group, it inherits
that planet's position automatically — moon and ring travel with the
parent with no code coordinating the two. That's also what makes the
relationship legible: a project visibly belongs to a domain because it
moves with it.

And because placement comes from a hash of the project id (§49), a project
sits in the same spot on every load and for every visitor. Adding a
repository next year slots it in without moving anything already there,
since nothing is positioned by index alone.

Right now the four visible fixtures appear as moons on Web (2), AI, DSA and
Other. The hidden fixture correctly does not.

## Counts appear only when there is something to count

An empty domain shows no number, not a zero. "0 projects" reads as a
finding about Khush's work; the absence of a count reads as what it
actually is — nothing analysed yet (§62).

## Data now comes from the server

`page.tsx` is an async server component and calls `getDataSource()` there,
passing projects down as props. This keeps the data source server-side, so
chunk 12's swap to Prisma needs no client changes at all — which was the
whole point of putting the seam in at chunk 02.

# Chunk 05c — the central star

No new dependencies.

## Changed

| File | Why |
|---|---|
| `src/components/universe/Scene.tsx` | Layered corona; camera pulled back. |
| `src/components/universe/UniverseCanvas.tsx` | `K` glyph and the name at centre. |
| `src/components/universe/OrbitFallback.tsx` | Flat star matched to the new proportions. |
| `src/lib/universe.ts` | `STAR_RADIUS` 1.15 → 1.75, `BASE_ORBIT_RADIUS` 4.2 → 4.6. |

## Glow without a bloom pass

Brightness comes from three stacked additive shells rather than
post-processing. §50 asks for minimal post-processing, and bloom means an
extra full-screen render target every frame — expensive on exactly the
mobile GPUs this most needs to stay smooth on. Three transparent spheres
cost almost nothing and read as light at any resolution.

The two inner shells breathe slightly out of phase. In phase they read as
one object scaling; offset, they read as light.

This is the deliberate exception to §8's "use glow sparingly". The star is
the focal point and the only light source in the scene — the restraint
everywhere else is what lets it carry weight.

## Two things the size change broke

Worth recording, because neither was visible without doing the arithmetic:

**The AI orbit ran through the star's outer glow.** At the original scale
the innermost orbit sat at 4.20 and the enlarged corona reached 4.55, so
the AI planet would have passed through it every revolution. Fixed by
trimming the outer shell to 2.2× and pushing the base orbit to 4.6, which
leaves 0.75 units of clearance.

**The outer orbits were already off-screen — before this change.** At the
old camera distance the visible half-width was about 12.4 units while the
Academics orbit sat at 14.07, so it was being clipped the whole time and
nothing in chunks 04 or 05 surfaced it. The camera now sits at
`[0, 10, 24]`, which frames the full system down to a 1.4 aspect ratio.

## The K is HTML, not a texture

Painting the letter onto the sphere would turn it away from the viewer as
the star rotates, and text drawn into a canvas can't be selected or read
aloud. It's positioned by projecting the origin to screen space each frame,
the same mechanism the domain labels use.

The name below the star is ordinary page content for the same reason as
everything else in §61 — the 3D view reinforces information, it never holds
it alone.

# Chunk 05d — zoom and card sizing

No new dependencies.

## Changed

| File | Why |
|---|---|
| `src/components/universe/Scene.tsx` | Camera rig accepts a zoom multiplier. |
| `src/components/universe/UniverseCanvas.tsx` | Wheel handler, interaction legend. |
| `src/components/universe/OrbitFallback.tsx` | Equal-height domain cards. |

## Scroll zoom, without trapping the page

Capturing the wheel inside a section is how a page becomes impossible to
scroll past. So the wheel is only intercepted while there is zoom left to
give: once the multiplier clamps at either end, the handler returns without
calling `preventDefault` and the browser scrolls the page normally.

That makes reaching the limit the gesture for continuing past the section —
which is what a visitor will instinctively try anyway.

Range is 0.42× to 2.4× of the home distance: close enough that the star
fills most of the frame, far enough to hold every orbit out to Academics.

Zoom lives in a ref, not state. A wheel gesture fires dozens of events a
second, and routing each through React would re-render the scene tree to
move a camera.

The camera scales its home position rather than dollying along the view
axis, so it keeps its angle on the system as it pulls back. A straight
dolly would flatten toward a top-down view at the far end.

## Why the cards were different heights

The grid was stretching each `<li>` to the row height correctly — but the
`<button>` inside had `w-full` and no `h-full`, so it shrink-wrapped its own
text and left the cell partly empty. Domains with a two-line blurb therefore
looked taller than domains with one.

Fixed with `h-full` plus `flex-col` on the button, and `flex-1` on the blurb
so it absorbs the difference. Titles now sit on a common baseline across
each row.

## The legend lists only what works

Hover, click, scroll. The reference mockup also shows "drag to navigate",
which isn't implemented — there are no orbit controls yet. Listing it would
promise an interaction that does nothing.
